# 原版与 compact v4：新任务独立对比方案

状态：**供审阅，未授权执行，新增模型调用为 0。** 当前研究线已发生的调用仍为
182 次，历史七份缺失的公开最终用量继续标为未知。本方案不是一次新的实验结果。

建议只考虑一批预先固定的正式验证：**8 个新缺陷 × 每项 5 对 × 两个版本 = 最多
80 次调用**。沿用已有验收门槛，这已经是最小规模；不保证 80 次一定得到明确结论。
暂不做额外试跑，不在结果不显著时追加调用，也不把旧结果并进新样本。

- 原版：完整 `diagnosing-bugs`，指纹
  `3cf6b2fea38acbdebfbaca564f7a2f10cd7d12dfcad0442756a6842db96eccc1`。
- 候选：完整、未改动的 compact v4，指纹
  `db5e96d06d52f3c1fbfe4a10b12c999c6191dc6a42f889e074931730ff6eafa9`。
- 不测试已被拒绝的读取草案，也不拿这些新任务继续修改 v4。若用新任务结果调优，
  它们就成为开发集；下一候选必须换新的验证声明。
- 两组使用相同的修好后的 diff 工具、提示、夹具、模型配置、时限和结果检查。
  这里比较 Skill 版本；不估计工具开关的因果收益。

完整提交、父提交、功能文件和每项六组结果检查列在
[输入清单](2026-10-15-independent-comparison-inputs.json)。选择基于真实维护者修复，
没有调用模型校准难度，也没有根据新任务的 Agent 表现选题。

## 预计用量与停止线

估算数据是三个不可变公开归档中的 **130 次完整原版/v4 调用**：已完成验证 80 次、
中止后续批次中已完成的 46 次、机制验证 4 次；两组各 65 条。另一次失败调用没有
完整计数，不参与数值预测，但仍保留在历史账本；33 份未调用条目不是调用。
不混入已拒绝读取草案的用量，也不把这些历史质量结果混成新验证证据。

参考情景按各组历史均值乘未来各 40 次。保守情景按各组单次用量第 90 百分位乘
40 次，再加 25% 余量；总输入用缓存与未缓存两项相加，保持分区一致。这些是预算
情景，不是置信区间、费用承诺或一定够用的上限。新仓库，尤其较大的 Commander
源码，可能超过历史水平。没有假设四次机制验证的 27.76% 节省会继续出现。

| 指标 | 历史均值参考 | 保守预算情景 | 建议后续调用停止线 |
| --- | ---: | ---: | ---: |
| 总输入 token | 约 2,076.00 万 | 约 3,888.19 万 | 4,000 万 |
| 其中缓存输入 | 约 1,803.81 万 | 约 3,418.88 万 | 3,600 万 |
| 其中未缓存输入 | **约 272.19 万** | **约 469.31 万** | **500 万** |
| 输出 token | **约 62.41 万** | **约 116.29 万** | **125 万** |
| 调用耗时 | 约 5.50 小时 | 约 10.50 小时 | 12 小时累计调用耗时 |

缓存输入是总输入的一部分，不能再加一遍。耗时不与控制器的整体墙钟时间相加。
上述时间不包括离线准备和归档，不能据此承诺完成时刻。供应商账单、内部重试、当前
账户的金额定价，以及完整编写/编排用量无法从这些记录得出，不编造美元费用。

停止线属于**拟议的逐次检查**，还不是已实现的 API token 硬上限。达到任意一条就
不再启动后续调用；正在执行的一次可能使最终用量越线。不能为了凑满 80 次越过停止
线继续跑。预算检查器必须先通过离线验证，之后才可用于任何已授权的真实执行。

## 验收标准不降低

继续使用既有 schema 2 的 `efficiency` 策略，指纹
`e6c0610daccd82f4fa326fb2660ae9f6dc722e1544f1caa006b4143de3da4a5e`。
规则来自 [冻结的统计协议](../metrics.md#explicit-efficiency-acceptance-policy-version-2-unreleased)，
不是看到结果后再选门槛。

1. **正确性没有可见退步。** 任一配对、任务、分数或具名检查出现退步，即不能接受；
   不能用其他任务的收益抵消。全部通过而质量持平时，质量判定仍为 `inconclusive`，
   不说成正确性提升或等效性证明。
2. **节省至少 10%，并有保守边界支持。** 主指标是“所有实际调用的未缓存输入 / 成功
   执行数”，失败调用也算成本。按完整任务块做 10,000 次固定种子 `20261013` 的
   bootstrap；95% 区间上界必须不高于 −10%。只看平均下降 10% 不够。
3. **改善要有覆盖面。** 至少 6/8 个任务各自降低该主指标；逐项列出全部成本增加。
4. **不把成本转移到其他分区。** 汇总的每成功执行总输入、缓存输入、未缓存输入和
   输出均不得增加；调用耗时每成功执行最多增加 25%。单项任务增加仍须披露。
5. **证据必须完整。** 8 项各 5 对完成，80 次均有完整最终五项成本、原生回执和
   可离线重放的交付；提前停、失败、缺用量、缺任务或验真不足均不能授权升级。

不增加试次直到显著，不降到 7% 或去掉难题，不只汇报完成的前缀。不承诺本批一定
通过。即便达到条件，也只是这个任务组合的建议采用资格，**不自动升级 Skill**，
也不抹掉以前 normalize-url 等已知成本退步。

## 中止与失败记录

- 执行器、路由、配置指纹、证据完整性、供电或计时出现异常，立即停止后续调用。
- 一旦最终用量缺失，停止；保留部分用量/未知状态，不把未知记作零。
- 触及任一预算停止线，停止；已花费的失败、排除和未完成工作全部保留。
- 已确认的配对正确性退步可以提前终止后续消耗，保留拒绝结果。普通功能失败作为
  观察保留，不重抽、不替换；任何提前结束的前缀都不能产生正面验收。
- 没有自动重试、补齐、替代任务或另开批次。后续预算需要新的决定。

## 开跑前仍需完成的离线工作

本轮完成的是选题、来源核实、候选/策略固定与预算复算，**不是已验真的正式 bench**。
不能拿目前的输入清单直接执行 `eval`。目前没有可运行的真实调用请求或计划指纹。

每项需要先用 Node 命令验证：原始代码确实失败，维护者的完整功能修复确实通过，
普通行为仍正常，以及保留的回归在原版失败、在交付和维护者修复通过。定时器使用
受控时钟；未处理拒绝在隔离子进程观测，避免靠真实等待或检查实现文本来判分。
检查器和参考修复在 Agent 工作区之外；不使用模型裁判或 Skill 过程打分。

p-limit 的队列依赖需要在夹具内固定源码与许可证，不能往项目或全局环境安装依赖。
异步上下文任务还涉及维护者的 package imports/stub 改动，不能只复制一部分功能补丁，
也不能把它需要修改的元数据误设成禁止修改。正式打包时明确允许修改的功能文件与
受保护资产；保留完整源码，禁止为省 token 任意裁掉上下文。

离线验真不通过就暂停该方案，先修查验问题；若必须换任务或改变题目行为，需要更新
清单并重新审阅，不能在已经开跑的批次里换题。准备好后冻结完整 bench、检查器、
两份 Skill、运行代码、CLI/配置、预算检查器和原生预览指纹，再按明确授权执行。
