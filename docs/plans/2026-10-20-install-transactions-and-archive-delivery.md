## 安装事务的拆分边界

文件事务已放入新的`src/install/transaction.ts`，必要的共享常量放在同层；命令层继续提供原有`BACKUP_SUFFIX`等导出作为兼容入口。最终命名可按源码调整，但事务核心不得反向导入`src/commands/`，依赖检查需要覆盖新核心目录。

命令层先处理profile、agent、路径、冲突、预览和确认，再按原顺序将规则、Skill文件和末尾lockfile交给事务。事务只负责文件暂存、备份、替换、验证回调、回滚和清理。内容校验与lockfile一致性校验在事务成功前完成；成功日志仍在校验及清理成功之后输出。

必须保留以下区别：用户内容的`.skillfit-bak`保留最早原件，后续更新不能覆盖；lockfile的备份按当前行为保留上一版；临时`.skillfit-restore`恢复本次操作前的状态。回滚失败时保留对应恢复副本，错误信息必须让用户知道哪些目标尚未恢复，不能误报“安装完成”。

保持现有命令参数、默认值、退出码、托管块、冲突分类、lockfile格式与常规输出。暂存失败保证安装目标和lockfile不发生部分更新，不夸大为所有目录/备份都零变化。多文件提交仍依赖出错后的尽力回滚，不新增“崩溃安全”承诺，也不顺带引入跨进程锁或自动重试安装。

现有`backupOnce`把`access`异常统一当成不存在，清理异常也可能覆盖最初失败。这些是待故障注入确认的审查点，不写成已复现结论。若复现会损坏首份备份、丢失恢复副本或隐藏恢复失败，在1.2先记录失败并以独立小修复恢复保护语义，再通过回归进入第2阶段；不通过放宽测试来完成机械迁移。

### 安装验收矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| dry-run、strict冲突、拒绝确认、无变更重装 | 保持原日志和退出行为；不应用目标/lockfile变更 |
| 首装、更新、binary资源、多个agent与user/project scope | 内容、路径、hash、托管块和lockfile与基准一致，外部用户文本保留 |
| 首份备份已存在、无法读取备份、重复更新 | 最早用户备份不被覆盖；权限错误不能被当成“没有备份” |
| 暂存失败、首个文件后rename失败、lockfile写入失败 | 所有已应用目标恢复操作前字节，新建目标移除，lockfile一致 |
| 写后内容/lockfile校验失败 | 与写入失败走同一回滚流程，不输出成功日志 |
| 回滚或清理自身失败 | 明确保留原始失败及恢复失败信息，保留需要的恢复副本，不错误清理 |
| setup与脱离原目录的bundle | 使用同一事务实现；搬迁后在临时用户目录完成预览、安装和重装，无源码checkout依赖 |

第1阶段以行为基准、故障回归和逐项归档盘点齐备为验收；第2阶段以保护回归、独立bundle验证、全量测试和依赖检查通过为验收。故障注入复用`node:test`和临时fs根，不靠真实目录权限或真实用户配置制造失败。文件权限及Windows差异必须有实际回归或明确限制。

## 归档外置的具体方案

### 固定来源和完整性

默认来源为当前公共仓库的固定提交 `56b4dc68e115475e197c6510c9cb2235a5ad2c62`。归档目录记录每个原始相对路径、完整SHA-256和精确字节数，下载地址由固定仓库、完整提交和该路径组成。固定提交的文件链接约定见[GitHub官方说明](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files)。不使用`main`、`latest`或可移动tag代替固定版本，也不把API返回的临时下载URL永久写入目录；[Contents API](https://docs.github.com/en/rest/repos/contents)明确说明了下载URL有效期。

首选直接读取现有Git原件，不新建存储服务或上传重复资产。GitHub Releases镜像作为后备提案，只有固定提交来源确实不能满足需求才另作具体review；不能在未验证时把镜像写成可用来源。

19个原件继续保留在仓库，路径和字节不变。阶段3必须逐个完成真实远端可用性与hash核验，再允许阶段4切换。断网时可从用户明确提供的本地归档根恢复；缺失或损坏时清楚报错，不把空文件或缺失归档当成功。

### 恢复入口和历史工作区

已新增随包分发的`evidence/fetch-archives.mjs`及版本化目录，保持零运行时依赖；本轮不增加第九个主CLI命令。脚本接口已实现并验证，以下命令在新包内可使用：

```bash
node ./node_modules/skillfit/evidence/fetch-archives.mjs --list
node ./node_modules/skillfit/evidence/fetch-archives.mjs --all --output ./historical-evidence
node ./node_modules/skillfit/evidence/fetch-archives.mjs --all --output ./historical-evidence --yes
node ./node_modules/skillfit/evidence/fetch-archives.mjs --all --output ./historical-evidence-offline --from ./archive-source --offline --yes
```

支持按目录中的稳定ID选择单个归档；`--list`和无`--yes`的预览不联网、不创建目录。实际操作仅写用户指定的新目标目录；已有目标直接拒绝。`--offline`保证零网络访问，本地来源同样必须通过字节数和SHA-256校验。普通CLI、npm安装和安装后脚本都不能隐式触发这些下载。

**下载19个tar文件还不等于保留回放能力。** 第1.3阶段必须登记历史脚本还需要的README、索引、冻结runtime、支撑文件及工作目录。恢复时从当前安装包复制经盘点的公开支撑文件，并按原仓库相对路径放置所选归档，形成独立历史工作区；支撑文件白名单由1.3盘点得出并随目录版本化，只复制明确允许的资源，不扫描整个checkout、私有lab或用户配置。目标目录不能位于来源目录内部，避免递归复制自身。恢复属于新输出写入，使用暂存及碰撞保护，不写安装器的配置lockfile或备份。

恢复工具只准备资料，不解压、不运行下载代码，不覆盖`node_modules/skillfit`或历史原件。暂存放在输出的同一父目录；所有文件校验成功后才提交为最终目标，提交时再次检查碰撞，覆盖“下载途中目标被创建”的回归，失败清理本次暂存且保留已有输出。下载设置超时、字节上限和HTTPS来源边界；404、截断、hash不符和连接错误必须是失败。

对于原先仅支持源码checkout、特定Node或特定系统的历史recipe，保留原限制，不能因为新增下载入口就宣称19项全部支持Node 22/Windows。所有19项须逐字节恢复；原有npm承诺可执行的流程须在脱离checkout后等价执行。缺少条件的历史回放单独标明，不能算作通过，也不能修改冻结脚本来迁就新包。若旧文档已承诺支持而基线缺文件，则登记为需要修复的既有问题，不得改标“不支持”来过关。

## 瘦包切换与兼容性门槛

临时演练已证明子目录`.npmignore`能够排除归档，符合[npm files规则](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#files)。实施候选是在`evidence/artifacts/`新增打包控制文件，按归档目录生成/校对19条精确路径规则。演练的通配符只用于验证机制，正式规则不能静默吞掉未来未登记的归档。

[包检查](../../scripts/check-package.mjs)及[策略](../../scripts/package-policy.json)必须同时调整：新归档目录、恢复工具和指南为必要文件；目录中的19个压缩包在瘦包中应全部缺席，但在源码固定提交中存在且hash一致；未登记的新归档仍然报错。不能简单删除旧的19个必带检查而不补替代约束。同一实现快照下比较切换前后清单，移除集合必须精确等于19项，新增的工具和支撑文件逐项说明，不能删掉其他旧文件来达成体积目标。

保留`evidence/inputs/`、冻结runtime/src/索引及已支持示例，继续保留原[0.12.0安装recipe](../releases/0.12.0-feature-smoke.mjs)需要的六个活动测试。新安装事务模块也必须出现在npm和bundle runtime中。

候选验收目标为**压缩不超过4 MiB、展开不超过19 MiB**，相对当前包压缩体积减少至少80%。上限由2.72 MB/17.88 MB的临时候选留出新实现和文档空间推得，须以最终实际tgz确认；超限先解释内容和检查遗漏，不能为过关静默提高上限或再删历史资料。

若远端不可用、离线恢复失败、支撑文件缺失或回放不能保持，停止瘦包切换，完整包仍可交付独立的安装事务重构。不要把尚未解决的兼容性问题藏在“发布后再补”。未来首次发布瘦包须采用新的版本和明确说明；当前本地0.12.0快照不能冒充注册表已发布归档。
