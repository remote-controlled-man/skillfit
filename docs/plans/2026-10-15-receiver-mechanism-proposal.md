## 顺序与第二次调用的门槛

1. **先运行 v4.1 候选一次。** 完成后先保存原生账本、交付、用量和计时，
   再离线验收、查看公开命令记录。
2. 只有候选功能全部通过、机制有实际执行证据、用量和计时完整、环境
   无异常，且所有成本均低于下表“第二次准入线”，才运行 v4 对照一次。
3. 任一条件失败或无法核实，停在第一次。第二次结束即停，不自动扩跑。

选择候选先行是为了减少无效开销，**不是随机试验或无偏估计**。
不因第一次的结果换任务、换版本、改提示词或反转顺序；不得用历史
v4 的一次失败冒充本批对照。旧 80 次方案已停止，其余 68 次不自动转用。

## 预算：硬限制与停跑线分开

执行次数硬限制为 **2 次**，两次均设 **600 秒（10 分钟）执行超时**。
两次最多占用约 20 分钟的执行器时间，输入准备、离线验收和人工审阅另计。
之前记录使用 1,200 秒超时，不能把新旧耗时直接合并为同一批统计。

| 维度 | 两次累计停跑线 | 第一次完成后的第二次准入线 |
| --- | ---: | ---: |
| 总输入 token | 600,000 | 必须小于 300,000 |
| 其中缓存输入 token | 500,000 | 必须小于 250,000 |
| 其中未缓存输入 token | 100,000 | 必须小于 50,000 |
| 输出 token | 20,000 | 必须小于 10,000 |
| 执行器耗时 | 1,200 秒 | 必须小于 600 秒，且无超时或计时异常 |

缓存与未缓存输入已经包含在总输入里，不能重复相加。第一次预留约一半
预算给对照；达到准入线就停，不能以“累计还没超”为理由继续。

**token 数值是调用之间的停跑线，不是运行中的硬封顶。** 现有执行器要在
调用结束后才能取得最终用量，已经开始的一次可能越线；冷缓存时第一次
就可能超过 10 万未缓存输入。保留实际超额和未知用量，不截断数字、
补记零或再启动下一次。若要求 token 绝不越线，当前执行器不满足该要求，
需要先有支持硬封顶的执行方式，不能把本方案当作这样的承诺。

预算参考来自[原失败批次的存档](../../evidence/artifacts/2026-10-15-independent-comparison-regression-stop/README.md)：

- 当时 v4 一次用了 197,021 输入（其中缓存 172,800、未缓存 24,221）、
  5,912 输出、184.285 秒。简单按两倍算，是约 **39.4 万输入、4.84 万
  未缓存输入、1.18 万输出、6.14 分钟**。
- 当时“上游原版 Skill + v4”两次合计是 406,851 输入、338,560 缓存、
  68,291 未缓存、12,749 输出、388.452 秒，即约 **40.7 万输入、6.83 万
  未缓存、1.27 万输出、6.47 分钟**。

这两种算法都只是预算参照。v4.1 尚无真实样本；第二组中的上游原版也
不是本方案的对照。它们不是新批次的预测区间或保证。未缓存停跑线约为
第二组参照的 1.46 倍；缓存命中、模型执行路径都可能改变实际消耗。
不估算未核实的账单金额，隐藏的服务端重试和完整编写成本仍未知。

## 验收与结果解释

候选功能必须同时满足：

- 原验收器 **6/6**：包含普通行为、两个接收者调用点、超时与 fallback、
  返回值和拒绝原因，以及有效回归测试；所有受保护文件保持不变。
- 额外接收者探针 **18/18**：严格函数、另一个执行环境的函数、已绑定函数，
  各覆盖原来的五条路径；其中另有 3 条直接调用控制。它们彼此相关，
  不能算作 18 个独立任务。
- 模型提交的回归测试必须在原缺陷上失败，在自身修复和维护者修复上通过；
  无注册测试、跳过、取消或超时都不算有效证据。

机制证据只查看实际执行的公开命令及返回结果，不索取或分析私有思维过程：

- 必须观察到实际成功读取对应 Skill，并能核实返回的指导内容；仅放入文件
  不算已经使用。
- 最终决定如何修复接收者之前，有可执行的区分性探针，能区分至少两个
  合理接收者选择；预期来自 API、调用方或独立运行的传入函数。
- 一句解释、测试名称或“我验证过”不算执行证据。正确修复但没有这些证据，
  单独记作“功能通过，机制未观察到或未知”，停在一次。
- 对照也必须有实际 Skill 读取和完整记录；否则不能支持两版本的机制比较。

| 观察结果 | 结论与行动 |
| --- | --- |
| 候选任一功能检查失败或出现新退步 | 保留失败，停在 1 次，不运行对照 |
| 候选正确但机制证据缺失或模糊 | 机制证据不足，停在 1 次 |
| 候选符合所有要求，对照在目标接收者行为或其错误回归预期上失败 | 仅记为本开发案例出现了预期差异 |
| 两版均通过全部功能检查 | 这一次没有区分两版本，不能归因于新增提醒 |
| 对照因无关错误失败、未读取 Skill，或记录不完整 | 对目标机制证据不足，不以它衬托候选 |
| 两次用尽 | 无论结果如何均停，后续另作决定 |

成本逐项报告两版本的输入、缓存、未缓存、输出和耗时及其涨跌；失败、
超时和未完成工作全部计入。每次成功成本只在确有成功时计算，否则为
`null`。任何额外成本都明确列出，不能用正确性修复替代成本结论。
单任务单对没有稳定性或因果效力，**不降低现有 8 任务 × 5 对的升级门槛，
不自动升级，也不据此自动申请或启动下一批**。
