## 各阶段怎么做以及怎样算完成

### 第 1 阶段 修正事实和行为说明

修改 [英文 README](../../README.md)、[中文 README](../../README.zh-CN.md)、[离线示例](../reproducible-offline-example.md) 和 [报告指南](../evaluation-reports.md)。先重新核对研究原文：Snyk 的 36.82% 是“至少一种安全问题”，提示注入分类检出率为 2.6%；论文引用必须固定版本并保留研究范围，不能拼接不同版本数字。核对入口为 [Snyk 正文数据表](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/)、[SkillsBench v4](https://arxiv.org/html/2602.12670v4) 和 [AGENTS.md 研究 v3](https://arxiv.org/html/2602.11988v3)。

命令说明以当前实现为准：区分普通报告与 `report eval --export --yes`，区分离线 `bench check` 与真实调用的 `--calibrate`，说明 `--decompose` 的单次 drafting 调用。已知失效链接为双语 README 的 quick-start 入口、离线示例的 README 入口、报告指南的成本章节入口。

完成条件：原文段落能支持修改后的表述，双语语义对应，4 个失效锚点修复；演示 console 内容保持原样，变更过的可执行示例用临时目录和离线替身验证。验证结果写入本计划，不改变 CLI 行为来迁就文档。

### 第 2 阶段 整理导航和状态来源

先增加目录，再调整双语 README 的阅读层次，保留现有文档路径。详细版本变化指向 CHANGELOG 和发布记录，专项实验过程指向证据索引，不再在多个入口重复维护同一累计数字。[证据总索引](../../evidence/README.md) 导航公开报告，[Skill 专项索引](../skill-evaluation-evidence.md) 解释对应研究序列；[路线图](../growth-roadmap-2026-10.md) 的版本状态以 [0.12.0 发布记录](../releases/0.12.0.md) 为依据。

在现有 `node:test` 体系中检查顶层文档、活动指南、文档目录和证据导航页的本地链接及锚点，处理重复标题、中文标题、显式锚点和代码围栏。固定历史副本不按当前版本语义改写。新增架构说明需对应真实文件职责，后续抽离模块时同步更新。

完成条件：从 README 能找到首次运行、case 编写、结果解释和开发入口；活动文档检查和双语对应检查通过。不得通过删除历史内容或批量改路径解决导航问题。

### 第 3 阶段 解除报告循环依赖

当前链路是 `eval-audit → eval-report → eval-single-arm-report → eval-audit`，`eval-acceptance` 也依赖命令层解析。检查 [报告模块](../../src/commands/eval-report.ts)、[审计模块](../../src/harness/eval-audit.ts) 和 [采纳模块](../../src/harness/eval-acceptance.ts)，将解析与纯数据校验放到 `src/harness/` 下一个职责明确的模块，命令层只负责读入、分派和展示。需要时保留原导出作为兼容入口，避免新增第二套解析器。

完成条件：编译后 JavaScript 的该循环消失，核心层不再反向运行时导入命令层；类型引用不误报为运行时依赖。当前受支持的 paired/calibration/trigger、完成/停止/不完整记录和历史汇总继续可读，损坏证据继续被拒绝，策略、费用和回放结果保持。

### 第 4 阶段 收拢 bench 业务

从 [bench 命令](../../src/commands/bench.ts) 中优先抽离完整性检查和 oracle/NOP 探测，沿用已有模板、source capture、drafting、calibration 和 verifier 执行模块。同步检查 [eval 预检](../../src/commands/eval-preflight.ts)、[校准](../../src/commands/bench-calibration.ts) 与诊断构造/渲染的职责，不能把业务函数搬走后仍让核心依赖命令层。阈值保持单一来源，现有通过源码位置核对阈值的测试跟随真实定义调整。

完成条件：原有 UNKNOWN/WARN/FAIL 分类、task 选择和顺序、超时、中断、零调用预览、输出碰撞与写入保护保持；相关测试及内置/贡献 bench 校验完成。不按行数目标拆文件。

### 第 5 阶段 验证分发内容

先检查 [打包范围](../../package.json)、[发布检查](../../scripts/npm-release.mjs) 和 [npm 首次运行测试](../../src/commands/npm-first-run.test.ts)，再形成保留/移除清单。保留 runtime、矩阵、支持的 bench/profile/driver Skill、schema、离线示例及其输入。现有请求示例依赖 `evidence/inputs/`；[0.12.0 安装验证](../releases/0.12.0-feature-smoke.mjs) 会运行包内部分测试，不能直接排除整个 evidence 或所有 `.test.js`。

在临时目录生成实际 `.tgz` 并离线独立安装或解包，隔离用户目录和凭据影响。验证帮助/版本、空项目 case 创建和检查、只读列表、eval/calibration 预览、synthetic report、安装预览，以及离线替身生成的 paired/calibration/trigger 回放、judge 和停止记录。归档迁移后再验证，不从源码 checkout 补缺。

完成条件：安装后支持的流程独立通过，记录精简前后体积、清单和保留理由；包清单检查能发现必要文件缺失、禁止路径和非预期归档。若精简需要取消已文档化离线能力或改变分发承诺，先记录方案并重新 review，不能为缩小体积静默破坏兼容。大型历史归档独立下载仅作为提案，不执行上传。

### 第 6 阶段 整体验收

在仓库根目录运行下方既有命令，并完成文档、依赖和归档安装检查。全量测试应无失败；贡献 bench 的现有警告按实际情况保留，不通过删断言或降级诊断消除。最后检查 diff 和 8 类原始发现的覆盖情况，交付实际完成项和明确延后项。

```bash
npm test
node dist/cli.js bench check benches/code-review
node dist/cli.js bench check benches/debugging
node scripts/check-contrib-benches.mjs
```

文档修改检查事实、链接和 diff，变更命令示例时验证对应离线路径；修改测试或实现后执行 `npm test`。相关检查通过后，没有新修改或未解问题不重复执行。CI 继续覆盖 Linux/macOS/Windows，但远端结果必须等实际运行后记录。

## 实施边界与恢复

保持现有 CLI 参数、默认值、退出码、JSON/manifest/schema、统计公式和采纳门槛；若必须改变公开合同，先修订方案。配置写入的确认、dry-run、备份、回滚和写后验证，以及新输出的碰撞保护保持。`install.ts` 的事务拆分明确延后，不计作本轮已解决。

不新增运行时依赖，不调用真实模型或真实 Agent，不改实际用户配置，不全局安装。固定的日期化证据、发布收据、回放 runtime 和脚本保持字节及路径；当前目录索引可维护，历史结论的更正另写日期化记录。`workspace4skills/` 不读取、不改动、不进入包或 CI；禁止 `git clean -fdx`。

每阶段保持最小可独立验证的 diff。验证失败时停在对应任务，记录失败及未完成范围，修复后再验收；不能用后续步骤掩盖失败。临时 bench、运行目录和归档使用新目录，不覆盖既有输出。若方案不可行，仅撤回本阶段自身变更，保留用户工作及原始失败记录。用户现已追加授权：全部改动复核、修复及验证通过后创建本地提交；推送、合并、发布及付费评测不自动执行。

## 已发现的依赖与决策

- **新发现与处理：** AST检查包含字面量动态导入，发现基线静态扫描遗漏的 `bench → eval-preflight → bench` 环。第3.2步将共享错误类单独提取并保留原导出；这是移除依赖环的最小调整，不提前重写第4阶段的bench业务。（2026-10-20）

- **发现：** 请求示例读取 `evidence/inputs/`，安装 recipe 运行部分包内测试。**影响：** 第 5 阶段必须先核对保留清单，不能直接按目录名或后缀裁减。
- **发现：** 文档测试目前从 `src/commands/bench.ts` 读取阈值。**影响：** 第 4 阶段移动定义时同步更新测试入口，保留断言。
- **决定：** 先修文档事实和导航，再改报告/bench，最后精简发布包。**理由：** 先建立清晰入口，再基于稳定运行时核对分发依赖，便于逐阶段定位回归。（2026-10-20）
- **决定：** 使用有序勾选清单记录真实进度，部分完成写明剩余工作，不把计划写完算作整改完成。**理由：** 用户要求能直接看出执行到哪一步。（2026-10-20）
- **复核结论：** 用户已授权计划 review 通过后按序实施。执行顺序及完成条件可行；README 精简保留原命令块和章节入口，包裁减先证明兼容，不承诺删除必须保留的历史材料。按第 1 阶段开始，不增加额外审批步骤。（2026-10-20）
