## 要解决的问题与边界

0.13.1先后运行代码PR/main、记录PR/main四轮三系统CI，此外预演/正式发布分别测试和打包。安装、Skill、归档、签名和收据主要由临时脚本及人工协调；反复查询状态/展开日志增加交互和token。

保留main现有规则集和三个必需名称：`test (windows-latest)`、`test (ubuntu-latest)`、`test (macos-latest)`。传统branch-protection接口返回404，但规则集接口确认PR和三个检查仍受约束，不能据此绕过。保留main-only、手动发布、`npm-release`环境、OIDC、单次上传和版本未占用检查；不增加发布凭证、机器人账号、运行时依赖或自动付费评估。

本轮保留**代码/工作流变更PR及main的两轮完整三系统CI**，不引入跨提交测试缓存的信任机制。减少的是记录变更重跑全量运行时测试、预演/正式重跑源测试和重新打包，以及同包人工重复验收。不能承诺尚未实测的耗时/token降幅。

## 执行顺序与验证方式

- [x] **1 调研、写计划及review。** 核对实际规则、必要检查、发布来源和失败处理；明确快速路径及复用的边界。验收：下方设计/失败矩阵无阻断项，先计划后改实现。
- [x] **2 收敛记录类CI并保留三个必需检查。** 仅允许计划Markdown、版本发布说明，以及新增版本化JSON/text收据走针对性验证；可执行文件、package/lock、公共调用文档、配置、bench、归档及任何未知/混合变更均跑全量。缺少/非法diff基准回退全量；删除/重命名及不确定变更不进入快路径。快路径仍在三系统构建，检查实际包、文档/Skill版本、链接、收据格式/摘要。代码路径保留现有测试和smoke。PR更新取消过期CI，main/发布不被新运行取消。记录真实测试计数、scope及提交到机器可读CI产物。验收：白名单/混合/删除/基准缺失/收据篡改回归通过，必需名称不变，不能把未执行的全量测试记成通过。
- [x] **3 同一来源只准备一份发布归档。** 预演要求准确main提交的完整三系统CI成功，构建/打包一次并验证，保存pack、tar、source SHA、CI运行和摘要。正式发布显式指定成功预演run，核对同仓库、工作流、main事件/来源、版本、run attempt、产物和完整性，发布原始tar；缺少来源或过期/篡改产物拒绝发布。预演/正式均不再另跑已完成的源测试；正式不再pack。验收：正向复用及错误仓库/来源/状态/attempt/缺失/篡改均有离线fixture；未占用与单次上传保障保留，未知CI证据不能放行。
- [x] **4 自动验收、收据及状态汇总。** 复用现有保护与冻结行为，把临时发布后程序转成通用仓库工具：registry version/latest/integrity、全新隔离安装及逐文件比较、Skill/当前文档及示例、功能recipe、19归档在线/离线和18回放+1导出、签名及精确来源。每个阶段只跑一次，记录pending/running/passed/failed及原始观察；安装暂不可见在同一有界可用性期限内重新读/安装，绝不重新上传。失败也保存状态、日志和摘要。自动生成带摘要引用的版本化收据、发布页/计划状态片段、总JSON及Actions摘要；提供单条校验/导入命令供正常Git交付，避免手抄/递归补状态PR。验收：fixture端到端验证调用次数、文件摘要、输出碰撞、失败保留和恢复只读；新通用recipe不修改旧recipe，零真实模型/用户配置写入。
- [x] **5 工作流整合与故障验证。** 用真实入口串联预演→原始tar复用→单次发布边界→自动验收→结果产物。常规测试离线，HTTP/registry/GitHub和命令执行使用注入或本地fixture；真实npm发布不用于测试。验证既有0.13.1数据兼容、未知历史归档recipe拒绝而非漏记成功，以及失败后verify-only新目录复验。验收：失败发生时其后依赖阶段不执行、成功收据不产生；状态/摘要仍生成，workflow无无条件成功或吞错。
- [x] **6 文档、最终review及交付准备。** 更新可信发布说明、脚本导航和CI约束；说明一次watch等待、成功仅摘要/失败才展开日志、收据导入、产物保留期及首次上线限制。核对diff、文档链接、包策略，执行一次最终`npm test`及适用的workflow静态检查，修复后复验。验收：实际结果与未执行项分开记录，计划6/6；交付实现和可review验证结果，本轮不冒充新流程已真实发布成功。

## 设计review与失败矩阵

| 位置 | 保留的保障 | 减少的重复及失败处理 |
| --- | --- | --- |
| CI范围 | 三个必需job始终存在；可执行/未知变更全量；记录仍检查真实pack、文档及摘要 | 严格小白名单，不能用workflow paths过滤让必需检查永久pending；数据文件不能顺带放行脚本 |
| 来源CI | 准确main SHA、同仓库CI工作流、完成且成功、完整三系统证据 | 一次读取结构化结果；未完成直接给出运行链接，不由模型循环查询 |
| 预演/发布 | 同版本、来源、环境、未占用检查，原始tar大小/摘要/清单核对 | 同一预演tar仅上传一次；正式必须指定预演，不自动挑选“最近一次” |
| npm暂不可见 | 保留20分钟上限及逐次观察，metadata和实际安装都要成功 | 有界退避在工具内完成；ETARGET/404不触发再次publish；完整性/认证错误直接失败 |
| 发布后验收 | 实际registry包、Skill/文档、功能、全部归档/历史程序、签名及来源 | 每项一次；不再由Agent手工另跑一套相同验收、拷贝数字和拼收据 |
| 状态/收据 | 原始失败追加保留，阶段未执行清晰标出，摘要引用可校验 | 一个状态文件生成JSON/Markdown/计划片段；不为记录自己的记录提交再创建状态PR |
| Git与长期留存 | 正常PR/CI；历史发布收据/证据不可变 | Actions产物不是永久Git记录；生成可导入文件并明确保留期，不新增自动推main/自动PR权限 |
| 等待 | 一个watch命令、退出码、最终一次结构化摘要；失败才取日志 | 工具内低频等待，Agent只汇报阶段变化/阻塞，不逐分钟重复播报相同状态 |

review结论：通过。额外检查了自动收据PR的权限/触发陷阱，本轮采用生成并校验导入文件，不新增写权限；主线完整代码CI不省。若实现中发现新约束，先更新本计划设计与验证依据再推进，不暗中缩减检查。
