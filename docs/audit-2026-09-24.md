# skillfit audit — 2026-09-24

**Status: draft for review.** This is not a contract and not a changelog entry. It is a findings list
produced by a full read of `src/`, `benches/`, `docs/`, and the contributor surface, intended to be
reviewed, triaged, and then either turned into issues or discarded. Nothing here has been fixed.

Baseline at time of audit: `main` @ `e1ced97`, `npm test` green (222 tests, 0 failures), build clean.

---

## 0. How to read this document

Every finding carries a **verification status**, because they were not all established the same way:

- **[verified]** — the cited source was read directly during this audit and the claim was confirmed
  line by line. Reproduction steps are given where they exist.
- **[reported]** — surfaced by an automated audit pass over the same files but *not* independently
  re-confirmed. Treat these as leads, not as established defects. A reviewer should confirm or kill
  each one before it becomes an issue.

Severities are about **blast radius on the project's own thesis**, not about lines of code:

- **T1** — the authoring path teaches users a wrong habit, or a gate reports green without gating.
- **T2** — a number the tool prints is wrong or untrustworthy.
- **T3** — robustness, safety, or self-inflicted breakage that does not corrupt a measurement.

## 1. The lens this audit uses

The stated product intent is **not** "ship a large library of benches." It is:

> Distil a *paradigm* for writing benches — mined from open-source projects and published work —
> small but complete, such that a user can apply it to their own situation and produce their own bench.

Two consequences follow, and they re-rank everything below.

**The bundled benches are teaching material, not product.** So "only 10 tasks, guidance says 20–50"
is *not* a defect. Coverage and difficulty-mix targets in `docs/metrics.md` §composition are advice
for a user's own bench, not a quota the bundled examples must hit. This audit does not raise it.

**Conversely, a wrong example is worse than a missing feature.** A user learns by copying
`benches/debugging/`. If that bench omits a step the paradigm declares mandatory, every downstream
user bench inherits the omission — and the tool currently does not object. That is why T1 outranks
T2 here, even though T2 bugs are more intellectually interesting.

A third consequence: the paradigm's knowledge is complete but **has no single home**. See §6.

## 2. T1 — the authoring path

### A1 · The oracle gate is optional and fails silently · [verified]

`src/commands/bench.ts:337`

```ts
if (task.oracle) {
  const oracleResult = await probeOracle(bench.dir, task.fixture, task.oracle, task.verifier);
  push(oracleResult.status, `${task.id}: ${oracleResult.message}`);
}
```

A task with no `oracle` field skips the gate with **no output at all** — not a WARN, not an INFO.

`docs/metrics.md:171` states the opposite: *"oracle solution passes the verifier at 100%
(**enforced**: register an `oracle` command per task and `bench check` fails when …)"*.

The oracle gate is the only mechanism that proves a task is *winnable* — that a correct solution
exists and the verifier recognises it. Without it, a task can be silently impossible and every arm
scores 0, which the tool then attributes to bench difficulty via the floor warning.

**Fix:** emit `WARN` (or `FAIL` under a `--strict` flag) when `task.oracle` is absent. The message
should say what is lost: "no oracle — task winnability is unverified."

### A2 · The bundled `debugging` bench has no oracles at all · [verified]

```
$ ls benches/debugging/ground-truth/
async-queue.md  chunked-decoder.md  debug-redaction.md  feat-slug.md  range-parser.md  ttl-cache.md
$ grep -c oracle benches/debugging/bench.json
0
```

Six tasks, zero oracle scripts, zero `oracle` fields. `bench check benches/debugging` reports
17/17 PASS with 0 warnings — because of A1.

This is disclosed honestly in `CHANGELOG.md` (*"The `debugging` bench intentionally has no oracles
yet — its command-kind tasks need verified reference patches, which are follow-up work"*), but
`docs/metrics.md:171` and `benches/README.md:54` do not carry the caveat, and a user reading the
bench directory sees only a green check.

**The cheap part:** the reference fixes already exist. Each `benches/debugging/ground-truth/*.md`
contains the corrected implementation as a fenced code block. Turning those into
`oracle-<id>.mjs` scripts is mechanical — the code-review bench already shows the shape
(`benches/code-review/ground-truth/oracle-r1.mjs` etc., 4 scripts, gate-validated in CI).

**Fix:** write the 6 oracle scripts, register them in `bench.json`, then land A1 so the omission
cannot recur.

### A3 · `bench check --calibrate` reports PASS after running nothing · [verified]

`src/commands/bench.ts:425` routes calibration through `runTriggerExperiment`, whose first act is
(`src/harness/trigger.ts:279`):

```ts
const eligible = plan.bench.tasks.filter((task) => task.shouldTrigger !== undefined);
```

Calibration is supposed to measure *inject-mode baseline difficulty*. It has no business depending
on trigger labels. But for any bench whose tasks lack `shouldTrigger`, `eligible` is empty, the run
loop never executes, and the summary at `bench.ts:454-456` evaluates:

```ts
push(discriminative === manifest.tasks.length ? 'PASS' : 'INFO',
     `calibration: ${discriminative}/${manifest.tasks.length} task(s) in the discriminative band …`);
```

`0 === 0` → prints `PASS  calibration: 0/0 task(s) in the discriminative band`.

**Why this is T1 and not T3:** `benches/contrib/README.md:13-15` instructs contributors to run
exactly this command and paste its output into the PR as the difficulty read. A first-time
contributor with an unlabelled bench follows the guide, spends an agent invocation, gets a green
line, and pastes a measurement that contains no measurements. The submission gate then accepts it.

**Fix:** two parts. (a) Fail loudly when `manifest.tasks.length === 0` — "calibration ran 0 tasks:
no task is eligible." (b) Decouple calibration from `runTriggerExperiment`; it should drive the
inject path with an empty skill bundle, which is what the surrounding code already intends
(`bench.ts:414-420` builds a `calibration-none` skill with an empty payload).

### A4 · The 2–8 facet-check rule is documented, unenforced, and violated by 4 of 10 tasks · [verified]

`benches/README.md:68` specifies *"the acceptance criteria decomposed into 2–8 named programmatic
checks"*. `bench check` never counts them. Actual per-task check totals, read from each verifier's
own `maxScore`:

| Task | Checks | Within 2–8? |
|---|---|---|
| `debugging/feat-slug` | **1** | no — under |
| `debugging/async-queue` | 6 | yes |
| `debugging/ttl-cache` | 8 | yes |
| `debugging/chunked-decoder` | **10** | no — over |
| `debugging/range-parser` | **12** (10 behaviour + 2 regression) | no — over |
| `debugging/debug-redaction` | **12** (5 behaviour + 5 regression + 2 secrecy) | no — over |
| `code-review/*` (4 tasks) | 2–3 | yes |

The rule exists because facet count drives the granularity of the Δscore signal: one check is
binary pass/fail wearing a costume (defeats the entire point of v2), and twelve checks over-weight
whatever they happen to measure. Neither bound is enforced, and the bundled examples — the thing
users copy — sit outside it in both directions.

**Fix:** `bench check` asserts the range from the verifier's emitted `checks` array. WARN outside
2–8, not FAIL, so existing benches degrade gracefully. Then bring the six tasks into range.

### A5 · `feat-slug` can be passed by rewriting the test file · [verified]

`benches/debugging/verifiers/feat-slug.mjs` in full is 23 lines; the grading core is:

```js
const result = spawnSync('node --test', { cwd: runDir, shell: true, encoding: 'utf8', env: scrubbedEnv() });
const passed = result.status === 0;
console.log(JSON.stringify({ passed, checks: [{ name: 'tests-pass', pass: passed }] }));
```

Three problems compound:

1. **No tamper guard.** The fixture ships `test/slug.test.mjs` *visible and writable* inside the run
   directory, and the verifier runs it in place. An agent that replaces the assertions with
   `assert(true)` passes. Four sibling verifiers defend against exactly this by re-running against a
   canonical pristine copy of the tests (`async-queue`, `chunked-decoder`, `debug-redaction`,
   `ttl-cache` all contain that comparison); `feat-slug` has none.
2. **One check** (see A4), so there is no partial credit to distinguish "implemented" from "cheated."
3. `spawnSync('node --test', { shell: true })` resolves `node` from PATH rather than using
   `process.execPath`, so the verifier can grade with a different Node than the harness runs on.

`benches/README.md:71` states the invariant plainly: *"A command verifier must fail on the untouched
fixture"*. It does. Nothing states the second half — that it must also fail on a *tampered* fixture
— but that is what makes the gate meaningful, and the other four tasks implement it.

**Fix:** port the canonical-test comparison from `ttl-cache.mjs` into `feat-slug.mjs`, add 2–4 real
edge-case checks (unicode, consecutive separators, empty input), and switch to `process.execPath`.

### A6 · `range-parser` regression checks are gameable · [verified]

`benches/debugging/verifiers/range-parser.mjs:34-39`:

```js
const testCount = (testSource.match(/\btest\s*\(/g) || []).length;
const regressionChecks = [
  ['regression breadth', testCount >= 4],
  ['boundary regression cases', /negative|maxItems|invalid|reject/i.test(testSource)],
];
```

`testSource` is read from the run directory — agent-writable. Four empty `test('x', () => {})`
blocks plus the word "invalid" anywhere in the file satisfy both checks. The 10 behaviour checks are
sound (they `await import()` the module and assert real return values); only these 2 of 12 are
hollow, but they are 2 of the 12 that set the score, and this verifier also lacks the canonical-test
guard the other four have.

Note also: despite `verifierKind: "command"`, this verifier never spawns a command — it imports the
module directly. That is fine functionally but means the `command`/`output` distinction in the
manifest does not describe what the verifier actually does.

**Fix:** same as A5 — canonical comparison, or assert on behaviour rather than on the test file's
text.

### A7 · Decoys are recorded but never penalised · [verified]

`benches/code-review/verifiers/seeded-bugs.mjs` (and the `review-r2` / `review-r3` variants built
from the same template) define a `decoys` array — plausible-but-correct code — and compute
`decoyHits`. Then:

```js
const checks = bugs.map((bug) => ({ name: bug.id, pass: hits.includes(bug.id) }));
const passed = missed.length === 0;
console.log(JSON.stringify({ passed, hits, missed, decoys: decoyHits, checks }));
```

`decoyHits` appears in the JSON for humans and **nowhere else**. It does not affect `passed`, does
not affect `checks`, does not affect the score. Flagging a decoy is free.

`benches/README.md:80` promises the opposite: *"Include decoys (plausible-but-correct code) so that
a treatment which simply 'reports more' is penalized by your scoring logic."* The scoring logic does
not penalise it. So the one structural defence against a verbose-treatment win is documented,
scaffolded, and inert.

Also gameable within the real checks: `missing-tests` is `anchor: /applyBulkDiscount/` with
`evidence: [/test/i]`, evaluated per line. Any single line containing both strings passes — e.g.
"applyBulkDiscount needs a test."

**Fix:** add a `no-false-positives` check that fails when `decoyHits.length > 0`, and tighten
`missing-tests` to require an actual assertion about coverage rather than the bare word "test".

### A8 · One check grades the agent's process, not its outcome · [verified]

`benches/debugging/verifiers/debug-redaction.mjs:257-260`:

```js
await check('regression', 'notes record the red-green commands', () => {
  const notes = readNotes();
  assert.match(notes, /RED\s*:.*node\s+--test.*fail(?:ed|ing)?/is);
  assert.match(notes, /GREEN\s*:.*node\s+--test.*pass(?:ed|ing)?/is);
});
```

This is satisfiable by writing the two strings into a notes file, with no relationship to whether
the red/green cycle happened. `docs/metrics.md:174` lists "grade the outcome not the path" among the
adopted contribution gates, and `docs/metrics.md:93` makes the same point from the evidence side
(Skill2Env's LLM-judged process rubric *cost* 4pp of task pass rate — process signals are exactly
what the design says to keep out).

It is 1 of 12 checks here, so the scoring impact is small; the teaching impact is not, because it
models a category of check the paradigm explicitly rejects.

**Fix:** drop the check, or replace it with an outcome assertion (the restored-leaky-implementation
test at `debug-redaction.mjs:250-253` already does the real version of this).

### A9 · Two prompts enumerate the grading checklist · [verified]

`benches/debugging/prompts/ttl-cache.md` lists, verbatim, the three seeded defects plus the
validation contract:

> - cached values such as `false`, `0`, and an empty string sometimes look missing;
> - a value can still be returned exactly at its expiry boundary;
> - repeated reads unexpectedly keep an entry alive even though this cache promises fixed, non-sliding TTL.
>
> … TTL must be a finite non-negative number; invalid TTL values must throw `TypeError`.

Those are the checks. The same shape appears in `range-parser.md`.

These are spec-implementation tasks in debugging costume. That is not automatically wrong — but it
means they measure "can the agent follow a precise written spec," which is close to saturated for
any current model, and it is a different capability from diagnosis. A user copying this prompt style
will build a bench that cannot discriminate. `bench check --calibrate` is the tool designed to catch
this, and per A3 it can report green without measuring.

**Fix:** for a diagnosis task, ship a failing repro and a symptom, not an enumerated defect list.
Keep one spec-style task deliberately, labelled as such, so the contrast is instructive.

### A10 · The `debugging` bench cannot be rehearsed offline · [verified]

No `fixtures/*/.skillfit-mock.json` exists anywhere under `benches/debugging/`, and
`bench.ts:343-344` short-circuits the mock probes for command-kind tasks:

```ts
if ((task.verifierKind ?? 'output') === 'command') {
  push('INFO', `${task.id}: command verifier — mock-arm probes not applicable`);
}
```

The reason is structural: `MockExecutor` produces `_output.md` text, while a command verifier grades
file state. So all six tasks are un-smoke-testable before spending tokens — which cuts against
`AGENTS.md`'s offline-testing rule in spirit, and against `benches/README.md:5`'s promise that
`bench check` validates a bench "before you spend a single token on runs."

**Fix (design question, not a one-liner):** either extend the mock marker to carry a *file patch*
for command-kind tasks, or have `bench check` run the oracle against the mock arm so at least the
winnability direction is exercised offline. A2 lands the oracles that would make the second option
possible.

### A11 · `benches/contrib/README.md` is a PR checklist, not an authoring guide · [verified]

Its five pre-PR rules assume the reader already knows how to build a case. It does not mention
`bench add --freeze`, `--decompose`, or `--from-commit`; does not mention `.skillfit-mock.json`,
`shouldTrigger`, negative controls, the 2–8 check range, or oracle registration. It links
`benches/README.md` once for "the same contract."

Worse, it routes contributors straight into the two broken gates: rule 2 requires `bench check` to
report 0 failures (which A1 and A4 make trivially satisfiable), and rule 3 requires the `--calibrate`
output (which A3 can fake).

**Fix:** this is the audience-facing half of the gap described in §6.

### A12 · Negative controls are 20% against a ≥30% target · [verified]

```
code-review:  1 false / 4 tasks = 25%
debugging:    1 false / 6 tasks = 17%
combined:     2 false / 10 tasks = 20%
```

`docs/metrics.md:168` and `benches/README.md:56` both specify ≥30%. Under the "examples are teaching
material" lens this is a mild finding on its own — but it means a user who copies the bundled
composition inherits a trigger bench that cannot measure false-trigger rate reliably, and
`bench.ts:385-390` only warns at *zero* negatives, not below the target fraction.

**Fix:** warn below 30% (not just at 0). Add two negative controls when convenient.

## 3. T2 — measurement integrity

These do not block the authoring story, but they determine whether the number a user gets at the end
of it means anything. All three headline items are **[verified]**.

### B1 · Executor errors are scored as trial failures · [verified]

`src/harness/runner.ts:162,166-182` — when the executor throws, `passed` stays `false` and the trial
is recorded with `error` set but `passed: false`. Then:

```ts
// runner.ts:243-245
function statsFor(records: TrialOutcome[]): ConditionStats {
  const passes = records.filter((r) => r.passed).length;
  const trials = records.length;          // ← errors included in the denominator
// runner.ts:324-326
function trialFlags(records: TrialOutcome[]): boolean[] {
  return [...records].sort((a, b) => a.trial - b.trial).map((r) => r.passed);
}                                          // ← errors become `false`, feeding discordantCounts
```

`docs/metrics.md:41-42` claims this is handled: *"if the agent never touched the fixture (empty
output, executor error), the trial is excluded from rates and reported as an error, not a failure
(**implemented**)"*. It is implemented in the trigger path (`trigger.ts:196-199`) and **not** in the
inject path.

One API timeout in one arm manufactures a discordant pair, which moves the pass-rate delta, the
McNemar p-value, and the bootstrap CI. At the 3–5 trial scale this tool targets, a single timeout
can flip a verdict.

**Fix:** filter `r.error === null` in `statsFor` and `trialFlags`, carry an `errors` count on
`ConditionStats`, and add a warning when any arm has errors. Mirror `trigger.ts`.

### B2 · No counterbalancing, and no seed is ever set · [verified]

`src/harness/runner.ts:460-469`:

```ts
for (const task of plan.bench.tasks) {
  for (const condition of CONDITIONS) {        // all baseline trials…
    for (let trial = 1; trial <= plan.trials; trial++) {
```

Every baseline run for a task completes before any treatment run. Any monotone drift over the run —
provider degradation, rate-limit backoff, thermal throttling, a filling context cache — is perfectly
confounded with condition.

`docs/metrics.md:27` says pairs share "the same fixture, prompt, and **seed**." A grep for
`seed|temperature` across `src/harness/executors/` and `src/matrix/agents.json` returns nothing: no
executor sets a seed or a temperature, and neither is recorded in the manifest. The only seeded PRNGs
in the codebase are the bootstrap (`stats.ts`) and the judge A/B order (`judge.ts`) — both correct,
neither relevant to the agent's own sampling.

**Fix:** interleave the loops (`for trial { for condition }`), or draw the order per trial from a
seeded PRNG and record it in the manifest. Separately: pass a seed/temperature where the agent
surface supports it, and record what was actually sent.

### B3 · The judge is not blind · [verified]

`src/harness/runner.ts:300`:

```ts
const judgeDir = join(plan.runsRoot, plan.runGroup, task.id);
```

That directory is the **parent** of `baseline/trial-N/` and `treatment/trial-N/`, and it is passed
as the judge executor's working directory (`runner.ts:309`, consumed at `judge.ts:86`). A
`--judge-agent` with file tools can read both arms' `_output.md` and their `_result.json` — which
names the condition and carries the skill bundle sha256.

`docs/metrics.md:127` promises "Blind pairwise comparison." The AB/BA position swap and
unanimity-only aggregation are implemented correctly (`judge.ts`, `runner.ts:268-282`); the
blinding premise underneath them is not.

**Fix:** run the judge in a fresh `mkdtempSync` directory containing only the two answer texts, and
write `judge-trial-N.json` to the task dir afterwards rather than using it as cwd.

## 4. T3 — robustness and self-inflicted breakage

### C1 · A partial `install` failure bricks the tool and reports falsely · [verified]

`src/commands/install.ts:484-492` writes files sequentially:

```ts
for (const item of writes) {
  for (const file of item.files) {
    if (file.backup) await fs.copyFile(file.path, file.path + BACKUP_SUFFIX);
    await writeFileAtomic(file.path, file.content);
```

`writeFileAtomic` is atomic *per file*; the loop is not atomic *across* files. If file 3 of 5 throws,
files 1–2 are already on disk, `validateWrites` (line 134) never runs, and `recordEntries` plus the
lockfile write (lines 140-141) never happen. On the next invocation, `planSkillItem` computes
(install.ts:427):

```ts
const pristine = entry !== undefined && missing.length === 0 && hashFiles(current) === entry.sha256;
```

`entry` is `undefined` because the lockfile was never updated → `pristine` false → `action:
'conflict'` → line 111 throws *"Nothing was written."* — which is untrue, and the state never
self-heals.

Two adjacent problems: `BACKUP_SUFFIX` is a single fixed slot (`.skillfit-bak`), so a second run
overwrites the good backup with the bad content; and the lockfile itself is written via
`writeFileAtomic` with **no backup**, against `AGENTS.md`'s "backup before write. No exceptions."

**Fix:** stage all files to `.tmp`, rename in one pass, update the lockfile as part of the same
commit, back up the lockfile, and make the recovery path able to adopt an unrecorded-but-hashed
write instead of hard-conflicting.

### C2 · `install --dry-run` exits non-zero on conflict · [verified]

`install.ts:109-112` throws on conflicts *before* the `opts.dryRun` early return at `:119-122`. A
dry run is supposed to report; it exits 1 instead. CI that runs `--dry-run` as a check fails on a
condition the check exists to surface.

## 6. The missing artifact

The paradigm's knowledge is complete and well-sourced. It has no single home.

| Where | What it covers | Written for |
|---|---|---|
| `docs/metrics.md` | **Why** — measurement model, with citations to SkillsBench, SWE-Skills-Bench, STARS, Skill2Env, Harbor, OpenAI and Anthropic eval guidance | implementers |
| `benches/README.md` | **What** — directory layout, `bench.json` schema, verifier contract, fixture rules | reference readers |
| `benches/contrib/README.md` | **How to submit** — five pre-PR rules | contributors who already have a bench |
| `benches/` (2 benches) | **What one looks like** | copiers |

What does not exist is the mainline: *here are the seven steps, here is why each one is
non-optional, here is one task walked end to end.* Today those seven steps are reconstructable only
by reading all four sources and reconciling them — and the reconciliation currently fails, because
the examples contradict the reference (A2, A4, A7, A8) and the gates do not enforce the rules (A1,
A3, A4).

For the stated product intent, **that document is the product**; everything else is support for it.

The seven steps, as the code and docs currently imply them:

1. **Start from a real failure.** Not a hypothetical. A bug that escaped, a task the agent botched
   twice, an incident thread. (`benches/README.md:79`, `contrib/README.md:8`)
2. **Freeze the scene.** `bench add --freeze --task <id> --prompt "…"` snapshots git-tracked files
   into `fixtures/<id>/`. Shrink it: keep the trap, delete the rest — every fixture file is inlined
   into the prompt, so size is tokens. (`benches/README.md:126-131`)
3. **Write the grader.** Either `--verifier-cmd`/`--expect` for the simple case, or
   `--decompose --agent <id>` to have an agent draft `verifier.mjs` + `oracle.mjs`. Decompose admits
   the draft only if both gates pass locally: the untouched fixture must fail (NOP) and the
   oracle-solved fixture must exit 0 with every check green (oracle). A draft failing either is
   discarded and nothing is written. (`benches/README.md:133-139`)
4. **Or mine it from history.** `bench add --from-commit <sha>` — the commit must touch at least one
   test file and one non-test file; the parent becomes the fixture and the fix's own tests become the
   hidden grader (SWE-bench FAIL_TO_PASS). Constraint: the fixture must run with **no build step and
   no installed dependencies**, so TypeScript repos and `node_modules`-dependent tests need
   `--include` narrowing or a hand-ported slice. (`benches/README.md:141-149`)
5. **Write the trigger variant.** `prompts/<id>.trigger.md` must present the work as files on disk
   with a natural request. Never inline a repository snapshot in trigger mode — measured at 0/9
   trigger recall with an inline snapshot versus the skill firing on the same tasks from disk
   (`docs/metrics.md:63-67`, `evidence/2026-09-trigger-snapshot-correction.md`).
6. **Label and load it.** Set `shouldTrigger` (true/false), include ≥30% negative controls, and plant
   decoys so verbosity does not win. Add `fixtures/<id>/.skillfit-mock.json` with `baseline` and
   `treatment` canned outputs so the bench runs offline. Record the seed answer in `ground-truth/`.
7. **Rehearse before paying.** `bench check`, then `--calibrate --agent <id> --trials 2` for the
   difficulty band, then `eval --dry-run`, then a real `--trials 3`.

Steps 3, 6, and 7 are where the current tooling does not hold the line (A1, A3, A4, A10, A12).
